**Facade, kernel, IO: live delivery and offline replay draw from a shared rng stream in a different ORDER, so a render can differ from the playback it claims to reproduce**

> **OPEN** as of 2026-08-23. [changes audio] Found while auditing the fix for the `b.render()` reproducibility finding above, and it is a different defect: that one was two renders disagreeing with each other, which is fixed; this one is a render disagreeing with LIVE. The two code paths order callbacks differently. Live, `packages/bellows/src/core/scheduler.ts:tick` iterates `for (const s of this.subs)` and delivers every tick inside the window for one subscription before moving to the next. Offline, `packages/bellows/src/bellows.ts:633` flattens every subscription's ticks and then `ticks.sort((a, b) => a.t - b.t)`. Those agree only while a window holds at most one tick per subscription, which is why it hides: the default horizon is 0.12 s and a quarter note at 120 bpm is 0.5 s. Measured with two subscriptions sharing one stream, `b.rng('shared')`, seed `order`: at `'4n'` and `'8n'` live and render agree exactly, and at `'32n'` (0.0625 s, so two land in one window) and `'16n'` they do not. Live drew A79, A90, B70, A83, B11, A94; the render drew A79, B90, A70, A83, B11, A94. The VALUES are the same sequence because one stream is drawn in order; which callback receives which value is what changes, so the two make different music from one seed. A stalled timer widens the window to `gap * 1.5` (scheduler.ts), so background-tab throttling can pull coarser subdivisions into the same failure.

`packages/bellows/src/bellows.ts:630-637`, `packages/bellows/src/core/scheduler.ts:tick`

This matters because of what the documentation promises. `apps/workbench/src/docs/pages/rendering-and-export.ts:27` says a render equals a fresh page load "provided two things are true: every random choice flows through `b.rng()` (never `Math.random`), and any other mutable state in your callbacks is derived from `step` or reset at a known step". The measured case satisfies BOTH provisos and still diverges, so the guarantee as written is incomplete rather than being misapplied by the user. Note the scope honestly: two renders of one seed do agree with each other, and one stream per concern (`'melody'`, `'drums'`), which is what every doc page and example teaches, never hits this. It needs one stream shared across two subdivisions.

Needs a decision rather than a fix, and both options change rendered audio for any piece that shares a stream. Either the live scheduler collects each wake's ticks across subscriptions and sorts by time before dispatching, which makes live match the replay and costs a sort per wake on the main thread (preallocated, since the audio path rule does not apply here but the allocation habit does), or the replay drops its sort and walks subscriptions in registration order, which makes the replay match live and is cheaper but enshrines what looks like an artifact of a loop rather than a design. Event placement is unaffected either way, because events carry explicit times; only which callback draws which number moves. A third option, documenting it as a caveat on the rendering page, is the cheapest and is the only one that changes no audio; that half is DONE on 2026-08-23, because leaving a claim on a live site that is known to be false in a reachable configuration is not a thing this repository does while a decision is pending. `rendering-and-export.ts` now states three provisos rather than two and names this one. The finding stays OPEN for the behaviour: the two orderings still disagree.
